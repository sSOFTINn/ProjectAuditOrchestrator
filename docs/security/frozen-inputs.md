# Frozen inputs for one scanner execution

This document describes the implementation's ownership, copying and lifecycle boundaries. Platform support requires acceptance of the exact PAO candidate and Docker Desktop version; the mechanism alone does not establish that compatibility.

## Ownership and writer model

PAO runs under the operator account. The configured workflow verifies its protected evidence/work parent before freezing. Legitimate toolchain, database, state and rules updaters change **original** paths. They do not receive or update PAO's random private copies. Scanner code executes in the reviewed VM with readonly input mounts and no writable host mount. Other unprivileged users cannot traverse the private base. The operator/coordinator and privileged administrators remain trusted: this mechanism does not prove resistance to arbitrary malicious code under the same account, root/SYSTEM or an administrator.

On Unix, the existing private parent must be owned by the current effective UID with owner-only permissions. Ancestors must be owned by that UID or root and must not grant another user write authority; a trusted sticky directory such as `/tmp` is allowed. Filesystems that cannot preserve these ownership/mode controls are refused. Windows creates each new base atomically with the existing protected private-DACL primitive, then holds its handle without write/delete sharing before copying any input bytes. Configured execution remains responsible for proving the existing parent DACL.

## API and invocation order

`FreezeInputs(ctx, spec)` returns a new `ExecutionSpec`, `cleanup func() error`, and an error. `FreezeInputsWithLimits` permits lower hard budgets for bounded tests or a stricter caller. Approval/freshness checks still belong to the Registry and runner. Freezing requires exact `ToolDigest` and, when `InputPath` is present, `InputDigest` from the already captured raw artifact. It grants no scanner execution authority.

Use the returned spec for capabilities and launch after Registry admission. The helper creates one `.pao-frozen-<random>` directory beside `spec.TemporaryDir`; its children contain the tool's original filename, the captured input's original filename and the complete state/database/rules trees. It remaps declared prerequisite paths in the argument vector. `TargetRoot` is already captured and is not copied again. `TemporaryDir` and output arguments stay bound to the runner's existing output policy. Only the single tool executable is copied: adjacent runtime files must be part of a verified prepared-state capsule or the reviewed runtime, rather than an implicit whole-directory mount.

Call cleanup after all host/container consumers have terminated and their mounts are released. Cleanup closes retained handles, checks the exact owned directory's identity and location, restores only recorded private-copy modes and removes that owned ephemeral tree. It never removes original prerequisites, target, output or arbitrary paths. Cleanup is idempotent. A failed identity/path check preserves the tree and returns an error; report that error rather than silently declaring cleanup complete. If container termination is unconfirmed, retain the copies until the lifecycle is resolved.

Docker cleanup verifies absence with an exact-name container query. A failed removal command is harmless only when a successful query proves absence; a failed query or a remaining container returns `CONTAINER_CLEANUP_UNCONFIRMED`. The runner preserves sealed copies and live-process leases and blocks subsequent launches in that PAO process. Joined evidence-persistence errors retain this typed failure. The ledger is process-local, not durable across restarts and not a coordinator for concurrent library calls. Configured CLI execution is sequential. Windows handles close when PAO exits; private readonly copies remain. The operator must separately confirm the exact container is absent and resolve the retained owned paths before retrying. This version provides no automatic recovery or cross-process admission barrier.

## Bytes, entries and identity

Default hard ceilings are 4 GiB per regular file, 8 GiB for the entire copied payload, 100,000 source entries, 100,000 created private entries and 16 MiB for one parsed capsule manifest. The file ceiling accommodates large database files without increasing the aggregate payload, entry or actual-I/O ceilings. Source reads and frozen readback/manifest reads additionally share a ceiling of three times the payload budget. Lower limits cannot exceed these hard caps. Directory listing retains only a bounded number of entries and one overflow sentinel. Directories, manifests, supporting database files, hidden entries and empty files are included; unlike target snapshots, these prerequisite trees do not skip `.git` or other undeclared content.

The copier reads no more than the opened file's initial size and the actual remaining budgets. It counts bytes actually read and written, checks cancellation between 32 KiB blocks, verifies regular file/identity/size/mode/mtime before and after I/O, and verifies the destination by bounded readback. Growth, replacement, short reads, unexpected files and unsupported special files result in refusal before launch. Cancellation checks are between bounded filesystem operations; they are not a claim that the OS can cancel every possible stalled storage syscall.

State, database and rules manifest digests are checked on the copied bytes. Their schemas, adapter/tool identities, kind, file set and all declared hashes, including database supporting files, are verified against copied readback hashes. Metadata parsing is bounded and retains the existing capsule field semantics. Registry approval of a license-data subset remains separate; the complete prepared-state capsule is frozen and verified. Repeated source hashing is not presented as an atomic-use guarantee.

Unix source traversal opens each ancestor with `O_NOFOLLOW` and opens descendants through held directory descriptors using `openat`; `O_NONBLOCK` avoids waiting on a FIFO replacement before metadata rejection. Windows opens reparse entries themselves and excludes existing/new write or delete handles during each copy. Existing source writers can therefore cause a safe refusal. Frozen Windows files and directories retain deny-write/delete handles through the whole consumer lifetime. Unix copies use an owner-only base; mounted descendants have readonly modes with original execute bits, allowing the non-root VM user to read the direct mounts while other host users cannot traverse the base.

## Docker CLI and bundled supervisor

`FreezeExecutableIn(ctx, path, digest, privateParent)` returns one verified native executable copy, cleanup and error. The caller must select an existing protected private parent. Prepare one host copy with frozen Docker CLI and bundled static supervisor **before** its capabilities and launch commands; keep both until all commands and container cleanup have finished. Direct launch must independently prepare and verify its inputs. Linux configured execution uses this copy mechanism; inability to provide a protected parent is a refusal, not a fallback to a mutable path.

Windows additionally exposes `PinExecutable(ctx, path, digest)`: it holds the original executable and all ancestors without write/delete sharing while checking its bounded hash. This preserves an installed CLI's adjacent-file layout. Unix `PinExecutable` refuses to imply that advisory locking excludes writers; callers use `FreezeExecutableIn` instead. Neither helper invents a Docker digest or enables a production fallback with an empty digest.

Catalog freshness is checked again after input copying and every Docker probe, immediately before actual launch. Runtime approval also remains current at that point. Crossing an expiry boundary during preparation refuses execution instead of relying on the earlier successful admission.

The single-file native copy does not copy or approve DLLs, shared libraries or plugins. The native command environment and commands must remain the runner's reviewed allowlist. Docker CLI compatibility, plugin discovery, Windows DLL behavior, actual Desktop share permissions and the exact bundled supervisor need platform acceptance on the candidate. The synthetic native test launches an inert copied Go test executable after replacing its original ancestor; it proves execution of the approved copied bytes, not compatibility of a production Docker installation.

## Test coverage and support boundary

Synthetic tests cover original updates after freezing, a source ancestor swap at the launch barrier, an explicit update barrier between copying and readback, tampering of every prerequisite type, undeclared files, metadata/identity mismatches, actual byte/entry/manifest caps, cancellation, growth and owned/idempotent cleanup. Windows tests exercise private DACL readback, junction refusal, retained write/delete/rename denial and native approved-copy execution. Unix tests cover descriptor anchoring after an ancestor/symlink swap, link/FIFO refusal, private-parent ownership and the in-place pin refusal.

Synthetic test coverage does not establish compatibility with every Docker installation. Release acceptance must separately cover the native Docker CLI, supervisor, non-root mounts and lifecycle cleanup on each supported host. Test and review reports are retained internally; this document is not a release approval.
