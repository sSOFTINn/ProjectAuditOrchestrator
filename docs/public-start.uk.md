# PAO: від архіву до офлайн-аудиту

Пакет `@PAO_VERSION@`, очікуваний тег `@PAO_TAG@`, базовий commit
`@PAO_REVISION@`. Локальна збірка з `source_state=modified` є кандидатом,
а не опублікованим схваленим випуском. Її точний склад визначає
`source_tree_sha256`. Звіряйте ідентичність через `pao version` і `pao doctor`.

## Перевірте пакет і Docker Desktop

Завантажуйте відповідний Windows AMD64 ZIP або Linux AMD64 tar.gz зі
[сторінки випусків](https://github.com/sSOFTINn/ProjectAuditOrchestrator/releases).
Перевірте SHA-256 та підпис тега за
[інструкцією цього випуску](https://github.com/sSOFTINn/ProjectAuditOrchestrator/blob/@PAO_TAG@/docs/release-verification.md).
Підписаний тег має зв'язувати commit із SHA-256 файла `SHA256SUMS.txt`.
Сама контрольна сума не підтверджує автора. Розпакуйте перевірений архів у
нову власну папку; команди нижче виконуйте з неї зі звичайними правами.

Підтримувані ОС — Windows 11 x64 та Ubuntu 24.04 LTS x64. Потрібен запущений
локальний Docker Desktop із Linux VM. Версії, перевірені саме для цього
випуску, наведені в його примітках. Встановіть Docker Desktop за інструкцією
для [Windows](https://docs.docker.com/desktop/setup/install/windows-install/)
або [Ubuntu](https://docs.docker.com/desktop/setup/install/linux/ubuntu/) і
самостійно прийміть застосовні умови. На Ubuntu потрібен доступ до KVM.
Звичайний Docker Engine, rootless Engine, remote contexts, ARM і macOS
не підтримуються. PAO не встановлює Docker Desktop і не приймає його умови.

Зберігайте весь розпакований пакет разом. Окрім PAO, він містить власні
`pao-sandbox-linux-amd64` та `pao-probe-linux-amd64`, десять декларацій
адаптерів, рецепти підготовки, порожні шаблони й ліцензії. Linux-помічники
виконуються лише всередині VM. Сторонні сканери, Python wheels, образи та
бази вразливостей до архіву не входять; їх отримує окремий онлайн-етап setup.
Go, source checkout і ручне складання JSON для першого запуску не потрібні.

## 1. Підготуйте синтетичну ціль

Почніть із нової папки й одного звичайного текстового файла без особистих
даних і справжніх ключів. Ціль має бути поза папкою пакета та інсталяції.
Нижче шляхи є прикладами: замініть їх власними абсолютними локальними шляхами.
Не використовуйте мережеві папки, junction або symlink.

Windows, PowerShell 7:

```powershell
New-Item -ItemType Directory -Path 'D:\PAO-demo-target'
Set-Content -LiteralPath 'D:\PAO-demo-target\README.txt' -Value 'PAO synthetic example'
.\pao.exe version
.\pao.exe setup --root 'D:\PAO-installation' --profile secrets
.\pao.exe setup --root 'D:\PAO-installation' --profile secrets --apply --target 'D:\PAO-demo-target'
```

Ubuntu, Bash:

```bash
mkdir -m 700 "$HOME/pao-demo-target"
printf '%s\n' 'PAO synthetic example' > "$HOME/pao-demo-target/README.txt"
./pao version
./pao setup --root "$HOME/pao-installation" --profile secrets
./pao setup --root "$HOME/pao-installation" --profile secrets --apply --target "$HOME/pao-demo-target"
```

Перша команда setup показує план без записів і мережевих запитів. Перевірте
джерела, версії, контрольні суми, місце зберігання та посилання на умови
використання. `--apply` попросить точне `PREPARE <plan-digest>` перед
завантаженням. Майстер використовує закріплені версії з пакета, перевіряє
завантажені байти та зберігає етапи для повторного запуску. Профіль `secrets`
готує Gitleaks; `mvp` — усі десять інструментів та потрібні бази й стан.

Повна підготовка та аудит `mvp` можуть тривати понад десять хвилин, особливо
на Windows: великі середовища ScanCode і бази перевіряються та копіюються.
Під час підготовки одного інструмента новий рядок може з'явитися не одразу.
Для короткої перевірки секретів використовуйте профіль `secrets`; він не
замінює решту перевірок повного профілю.

Підготовка потребує мережі; вміст цілі їй не передається. Без `--target`
майстер запитає шлях до підготовки, щоб перевірити розділення каталогів. Після синтетичних
перевірок він покаже фактичний склад установки й попросить ім'я оператора
та окреме `APPROVE <digest> AS <owner>`. Це рішення про готові байти й докази;
підтвердження плану не замінює його. Непідтверджена установка залишається
`PREPARED_NOT_APPROVED`. Не підставляйте вигадані імена, дати чи погодження.

Після завершення setup надрукує `config=<абсолютний шлях>`. Збережіть цей шлях
для наступних команд. Кожне налаштування пишеться в новий файл; старі конфігурації
не перезаписуються. Приватний installation root містить завантаження, покоління
інструментів, конфігурації, журнал, докази й локальні звіти. Не публікуйте його.

## 2. Перевірте готовність і виконайте аудит

У PowerShell підставте шлях, який щойно надрукував setup:

```powershell
$paoConfig = 'D:\PAO-installation\config\audit-REPLACE_WITH_PRINTED_ID.json'
.\pao.exe doctor --config $paoConfig --profile secrets --json
.\pao.exe audit --config $paoConfig --profile secrets
.\pao.exe audit --config $paoConfig --profile secrets --execute
```

У Bash:

```bash
pao_config='/absolute/path/printed/by/setup.json'
./pao doctor --config "$pao_config" --profile secrets --json
./pao audit --config "$pao_config" --profile secrets
./pao audit --config "$pao_config" --profile secrets --execute
```

`doctor --config` перевіряє права, журнал, хеші, склад ресурсів, строки
чинності й доступність потрібного Docker runtime. Він не читає вміст цілі,
не запускає сканери й не перевіряє ізоляцію контейнером. `READY` означає
готовність передумов профілю; це не висновок безпеки проєкту. `doctor` без
параметрів показує лише ідентичність PAO.

`audit` спочатку показує план, застосовність інструментів і відомі прогалини.
`--execute` просить точне `RUN <audit-id> <plan-digest>` поточного preview.
Якщо ціль, конфігурація або ресурси змінилися, попереднє підтвердження не діє.
Сканери працюють без мережі, з приватним read-only знімком цілі та ресурсів,
обмеженими output/scratch і timeout. Код цілі та package-manager scripts
не виконуються.

Для повного профілю повторіть setup з `--profile mvp`, виберіть нову
надруковану конфігурацію та виконайте doctor й audit з `--profile mvp`.
Після підготовки аудити не завантажують і не оновлюють нічого. Протерміновані
бази потребують нової онлайн-підготовки з новим `--root`; повторне погодження
не змінює їх вік. Той самий root/profile/recipe відновлює вже виконані етапи,
а не оновлює завершене покоління. Команди `--refresh` у цій версії немає.

## 3. Прочитайте результат

PAO друкує точні каталоги результатів. Приватний `run-summary.json` версії
`pao.dev/run-summary/v1` окремо показує стан виконання, покриття, потребу
перегляду, код завершення й шляхи доказів/звітів. Він містить локальні шляхи
й не є переносним публічним звітом.

Коди audit збережені: `0` — успішний preview, `3` — помилка конфігурації або
запису, `4` — результат потребує перегляду або виконання неповне,
`5` — скасування, застарілий preview чи блокування політикою. Код `4` може
супроводжувати технічно завершений запуск: це не збій програми й не clean verdict.
Точний статус дивіться у summary та звіті.

Повнота виконання не доводить повноти інвентаризації. Поточна локальна база
OSV охоплює Go; непідтримані екосистеми та формати залишаються прогалинами.
Оцінка sbomqs є інформаційною й не схвалює безпеку або ліцензії.

## Повторна перевірка, міграція й відновлення

Окрема синтетична перевірка готової установки:

```text
pao setup --verify --config ABSOLUTE_CONFIG_PATH
```

Команда запитує підтвердження, записує нові докази, пропонує окреме погодження
й друкує новий шлях config. Наступні doctor/audit використовуйте з ним.

Після зміни Docker CLI або runtime виконайте setup з новим `--root`. На Linux він готує
перевірену приватну копію Docker CLI; doctor нічого не копіює. На Windows
CLI працює зі встановленого розташування з перевіркою й утриманням його байтів.

Конфігурації v1/v2 доступні для preview; виконання потребує v3 зі спільним
`installation_state`. Майстер з `--import-config ABSOLUTE_OLD_CONFIG_PATH`
створить нову конфігурацію, збереже стару й підготує або повторно перевірить
завершені етапи. Старе погодження не переноситься автоматично.

Після аварії pending-запис у стійкому журналі блокує наступні залежні запуски.
Запустіть `pao doctor --config ABSOLUTE_CONFIG_PATH --profile mvp`: перевірка
`installation.journal` покаже точні ID незавершених запусків. У JSON вони містяться
в полі `pending_run_ids`. Використайте один із цих ID для перегляду відновлення:

```text
pao recover --config ABSOLUTE_CONFIG_PATH --run EXACT_RUN_ID
pao recover --config ABSOLUTE_CONFIG_PATH --run EXACT_RUN_ID --apply
```

Перша команда лише перевіряє стан. Друга просить `RECOVER <run-id>` і може
прибрати лише точно ідентифікований контейнер цієї установки; докази лишаються.
Якщо setup перервався до створення config, використайте `--state` зі шляхом
`INSTALLATION_ROOT/state` замість `--config` (Windows: `INSTALLATION_ROOT\state`).
Не видаляйте журнал, щоб обійти блокування.

Під час очікування вводу в `setup` або `recover` натисніть Ctrl+C, щоб вийти
без підтвердження дії. Уже підготовлені ресурси й докази зберігаються; скасування
не створює погодження і не запускає очищення контейнера.

Оновлюйте PAO в окрему папку, зберігаючи попередній перевірений пакет,
конфігурацію та докази. Новий пакет потребує власної setup-перевірки.
Повернення до старого пакета не поновлює прострочені погодження. Перед
видаленням установки окремо збережіть приватні докази й конфігурації;
автоматичного видалення або очищення PAO не виконує.
